🛡️ Remediation

SQL injection occurs when an application lets untrusted input become part of SQL syntax. This lab intentionally demonstrates that flaw using disposable sample records.

Here, the login handler concatenates the submitted username and password into a query string. The database parses the resulting text as SQL, so crafted input can change the query’s conditions.

❌ Vulnerable Code 
query = (
    "SELECT * FROM users "
    f"WHERE username = '{username}' "
    f"AND password = '{password}'"
)

results = connection.execute(query).fetchall()

Because the values and SQL syntax share one string, input can alter the meaning of the statement rather than being compared only as data.

✅ Secure Code 
query = (
    "SELECT * FROM users "
    "WHERE username = ? "
    "AND password = ?"
)

results = connection.execute(
    query,
    (username, password)
).fetchall()

The placeholders define the statement structure first; the database driver binds the supplied values separately. This is parameterized SQL using a prepared statement, so input cannot change the query structure.

Handle input deliberately

Validate expected formats, lengths, and allowed values where appropriate. Treat validation as a supplement—not a replacement for parameterized queries. Never try to remove “dangerous” characters as your SQL injection defense.

Limit database permissions

Give each application only the database access it needs. Avoid administrator-level accounts, restrict access to required tables and operations, and protect SQLite database files with appropriate operating-system permissions.

Handle errors safely

Log detailed database exceptions on the server for maintainers. Show users a generic error message; do not reveal SQL text, schema details, file paths, or credentials. This lab displays SQL error details only to help with local practice.

  • Use parameterized queries and prepared statements for every value supplied by a user.
  • Store real account passwords as strong password hashes. This lab’s visible sample passwords are for practice only.
  • Keep training data disposable and never connect an intentionally vulnerable exercise to real accounts or systems.
